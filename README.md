# staging_workshop_repo

A dbt workshop scaffold for declaring Snowflake sources and developing staging models. The instructor supplies the raw data in Snowflake; this repository contains no dataset.

## Repository contents

| Path | Purpose |
| --- | --- |
| `dbt_project.yml` | Project name, blank profile, resource paths, and default view materialization. |
| `models/staging/workshop/` | Source declarations, staging SQL, and model documentation/test templates. |
| `analyses/` | Exploratory SQL that dbt can compile without creating models. |
| `tests/` | Singular SQL data tests; column tests belong in model YAML. |
| `seeds/` | Optional small CSV reference datasets. |
| `macros/` | Reusable Jinja/SQL macros. |
| `snapshots/` | Historical tracking definitions. |
| `docs/` | Optional dbt documentation blocks. |
| `profiles.yml.example` | Snowflake connection template; actual credentials stay outside Git. |
| `.devcontainer/` | GitHub Codespaces environment that installs dbt Core and dbt-snowflake. |
| `requirements.txt` | Python dependencies for local development and Codespaces. |
| `packages.yml` | Empty optional dbt package list. |

Empty standard directories contain `.gitkeep` so Git retains them. `target/`, `logs/`, and `dbt_packages/` are generated by dbt and are ignored by Git.

## Instructor: prepare the workshop

1. Create a GitHub repository named `staging_workshop_repo` and upload this folder's contents, including `.devcontainer` and `.gitignore`. Keep `dbt_project.yml` at the repository root. You may enable GitHub's template repository option so participants can create their own copies.
2. Populate the workshop brief below with table details and tasks. Replace the placeholders in `_sources.yml.example`; rename it to `_sources.yml` when ready. Keep the staging examples as `.example` files if participants should write their own models.
3. Supply Snowflake account, user, role, warehouse, raw database/schema, and output database details. Grant access to read the raw tables and create views in each participant's output schema. Use a separate output schema per participant to avoid overwriting one another's models.
4. Choose the class authentication method. The connection template uses key-pair authentication; register each participant's public key in Snowflake. For Codespaces, make the private key available securely outside the repository and use its container path. Local browser SSO is an alternative when configured for the account.
5. Test the setup with a participant account and pin `dbt-snowflake` to the version you tested in `requirements.txt`.

The `profile` value is deliberately blank. Participants must fill it before dbt commands can run. `.example` files are inactive teaching templates; this scaffold has no active sources or models until they are populated and renamed.

## Participants: local setup

Install Git and Python 3.11, clone the repository, and open its root in VS Code:

```sh
git clone https://github.com/<OWNER>/staging_workshop_repo.git
cd staging_workshop_repo
python -m venv .venv
```

Activate the virtual environment:

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

```sh
# macOS / Linux
source .venv/bin/activate
```

Install the command-line tools:

```sh
python -m pip install -r requirements.txt
```

Copy `profiles.yml.example` to `profiles.yml` in the repository root. Fill in the Snowflake values and your authentication details. `profiles.yml` is ignored by Git. Set `profile: "workshop"` in `dbt_project.yml`, matching the top-level key in your profile. You can use another name if both files agree.

The profile's database and schema specify where dbt creates your views. The source YAML specifies where dbt reads the instructor's raw tables. Keep these locations distinct as directed by the instructor.

## Participants: Codespaces setup

On GitHub, choose **Code → Codespaces → Create codespace**. The dev container installs the same Python dependencies automatically. Complete the profile steps above using the Codespace's file paths and instructor-provided authentication method. Browser SSO can require additional remote-browser configuration; use the instructor's key-pair method for this scaffold.

## Develop sources and staging models

1. Rename `_sources.yml.example` to `_sources.yml` if the instructor has not already done so. Define the input database, schema, and raw tables.
2. Create a `.sql` staging model for each source table, using the SQL example as a starting point. Select columns explicitly, rename them consistently, cast types, and apply appropriate light cleaning.
3. Rename `_models.yml.example` to `_models.yml` and document the models and columns. Add tests that reflect the actual data rules.
4. From the repository root, run:

```sh
dbt debug --profiles-dir .
dbt parse --profiles-dir .
dbt compile --select path:models/staging --profiles-dir .
dbt build --select path:models/staging --profiles-dir .
```

`debug` checks the connection; `parse` validates project definitions; `compile` renders SQL; `build` creates staging views and runs their tests. Compilation may contact Snowflake for introspection or macros. After building, look for the views in your profile's output database/schema.

If you already maintain a profile in `~/.dbt/profiles.yml`, you may use that instead and omit `--profiles-dir .`. Match its profile name in `dbt_project.yml`.

Do not run `dbt init` inside this scaffold: the project already exists. These instructions use the dbt Core CLI; the dbt Fusion VS Code extension has a separate runtime and setup process.
